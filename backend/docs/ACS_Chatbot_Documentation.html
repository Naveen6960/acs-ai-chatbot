Section 1

Project Overview

What is this project?

The ACS AI Chatbot is an internal tool built for New York City's Administration for Children's Services (ACS). Child welfare employees — caseworkers, supervisors, and other staff — deal with complex policy documents on a daily basis. The most important of these is the CONNECTIONS DCP Manual, a lengthy PDF that describes procedures, protocols, and regulations for child protective services work.

Before this chatbot existed, employees had to manually search through the manual to find answers. That takes time and is error-prone. The chatbot lets employees type a plain-language question and get an immediate, AI-generated answer backed by the actual policy document. The system is powered by Azure OpenAI (GPT-4) and deployed internally at ACS.

What problem does it solve?

  • Reduces time caseworkers spend searching policy documents
  • Improves consistency in how policies are interpreted and applied
  • Provides a searchable, conversational interface to a complex body of text
  • Tracks usage for compliance review and audit purposes

What did I (Naveen) contribute this summer?

When I joined, the chatbot had basic chat functionality but nothing else. It had no memory — every page refresh wiped the conversation. There was no audit trail. Employees couldn't see their past chats. The backend was on an older version of Spring Boot and had no logging.

By the end of the internship, I added 6 features that transformed it from a basic demo into a tool ready for real daily use. The full list is in the Features section.

Who are the users?

ACS child welfare employees who are logged in via ACS Microsoft credentials. The chatbot is internal-only — not accessible to the public.

Installation & Setup

Before you start

You need access to the ACS Azure credentials and the database connection string. Contact Larisa Isakov or Manish to get these. Without them, the backend will not connect to Azure OpenAI or the database.

Prerequisites

  • Java 17 or higher installed (java -version to check)
  • Node.js and npm installed (node -v to check)
  • Angular CLI: npm install -g @angular/cli
  • IntelliJ IDEA (Community or Ultimate)
  • Git access to the repository
  • Azure credentials for OpenAI API and Azure SQL (get from supervisor)

Step 1 — Get the code

Clone or obtain both the frontend and backend from the team repository. The backend folder is named backend-java-api-app-4.0.6. The frontend folder is [TO BE CONFIRMED — ask Larisa or Manish for the frontend repo path].

Step 2 — Configure the backend

Open src/main/resources/application.properties in the backend project. Fill in the Azure credentials where marked. The file currently contains real Azure values — do not commit secrets to a public repository. Key properties:

# Azure OpenAI
azure.openai.endpoint=[INSERT AZURE OPENAI ENDPOINT]
azure.openai.api-key=[INSERT API KEY]

# Azure SQL Database
spring.datasource.url=[INSERT JDBC CONNECTION STRING]
spring.datasource.username=[INSERT DB USERNAME]
spring.datasource.password=[INSERT DB PASSWORD]

# How many recent chats to return per employee (currently 10)
acs.numOfRecents=10

Step 3 — Run the backend

Open the backend folder in IntelliJ IDEA. Let Maven download dependencies (it does this automatically). Find the main application class and click the green Run button. The backend starts on port 8080. You should see Spring Boot startup logs in the console.

Step 4 — Configure the frontend

Navigate to the Angular frontend project folder. Check proxy.conf.json — it should route /api/* to http://localhost:8080. If you're running the backend on a different port, update this file.

Step 5 — Run the frontend

cd [frontend-folder]
npm install
ng serve

The frontend starts on port 4200. Open http://localhost:4200 in your browser. Log in with your ACS Microsoft credentials.

Step 6 — Verify

  • You should see the ACS AI Chatbot UI
  • Log in — you should be redirected back after MSAL authentication
  • Type a question — you should get an AI response
  • Check SSMS: a new row should appear in dbo.chatlog with your employee ID
  • The conversation history sidebar should show your chat

Section 10

Database

The database is hosted on Azure SQL (Microsoft SQL Server in the cloud). You can connect to it using SSMS with the credentials in application.properties.

Table: dbo.chatlog

This is the only table added this summer. It stores one row per conversation turn.

ColumnTypeKeyNullableDescription
logidINT or BIGINTPrimary Key, Auto-incrementNoUnique ID for each chat record
employee_idVARCHAR—YesEmployee email from MSAL, e.g. naveen.kshirasagar@acs.nyc.gov
questionVARCHAR(1000)—YesThe question the employee asked. Truncated to 1000 chars if longer.
answerVARCHAR(1000)—YesThe AI-generated response. Truncated to 1000 chars if longer.
creation_timestampDATETIME—YesWhen the conversation happened. Set automatically by the backend.
Note on truncation

Questions and answers longer than 1000 characters are automatically cut to 1000 before saving. This is intentional — Azure SQL column constraints. If longer storage is needed in the future, increase the column size in the schema and remove the truncation logic in ChatLogServiceImpl.java lines 41–42.

Configurable limit: numOfRecents

The number of recent conversations returned for a given employee is controlled by a configuration property, not hardcoded:

# application.properties — line 97
acs.numOfRecents=10

Change this number to adjust how many past conversations appear in the sidebar. Restart the backend for the change to take effect.

Section 11

Backend (Spring Boot)

ChatController.java

This is the main entry point for all chat-related HTTP requests. It lives at com.example.azureopenaiapi.controller.ChatController.

// ChatRequest — the shape of data sent from the frontend
public static class ChatRequest {
    public String prompt;       // the user's question
    public String agent;        // which AI agent to use
    public String employeeId;   // employee email from MSAL
}

ChatLogServiceImpl.java

This class does the actual database work. Key methods:

  • getAllChatLogEntity() — returns most recent logs (limited by numOfRecents)
  • saveChatLog(employeeId, question, answer) — saves one conversation to Azure SQL
  • getRecentChatsByEmployee(employeeId) — returns last N chats for one employee

The numOfRecents value is injected from application.properties via @Value("${acs.numOfRecents}").

Request lifecycle

POST /api/chat
  → ChatController.chat()
  → OrchestratorAgent.process(prompt, employeeId)   [calls Azure OpenAI]
  → ChatLogService.saveChatLog(employeeId, prompt, response)
  → ChatLogServiceImpl saves to Azure SQL
  → Returns response to frontend

Section 13

Authentication — Microsoft MSAL

What is MSAL?

MSAL stands for Microsoft Authentication Library. It handles the ACS employee login using their existing ACS Microsoft credentials. When an employee opens the chatbot, MSAL redirects them to the Microsoft login page, they log in, and MSAL gives the frontend an authentication token that proves who they are.

What was already there (pre-existing)

The Microsoft login flow — the redirect, the login screen, the token — was already implemented before this internship.

What I fixed (Naveen)

Although MSAL was handling login correctly, the frontend was not using the token to identify the employee. The employeeId field in every chat request was null. This meant the database could not track which employee sent which message, and the conversation history feature could not work.

I fixed the Angular authentication service to correctly extract the employee's email address from the MSAL account object and include it as employeeId in every HTTP request to the backend.

How to verify it works

  1. Log in to the chatbot
  2. Open Chrome DevTools → Network tab
  3. Send a chat message
  4. Click the POST /api/chat request in the Network panel
  5. Under Payload, you should see "employeeId": "yourname@acs.nyc.gov"

Frontend (Angular 17)

Main file: app.component.ts

The core of the Angular frontend. It handles the chat message loop, renders the conversation, manages the sidebar state, and makes HTTP calls to the Spring Boot backend.

Key features in the UI

  • Chat window: Pre-existing. Displays the conversation between the employee and the AI.

  • Conversation history sidebar: Added this summer. Shows past conversations, loads them on click.
  • New Chat button: Added this summer. Clears the current conversation and resets the interface without a page reload.

proxy.conf.json — critical configuration

This file is essential. Without it, Angular (running on port 4200) cannot communicate with the Spring Boot backend (running on port 8080) due to browser cross-origin restrictions. The proxy file tells the Angular dev server to forward any request starting with /api to http://localhost:8080.

{
  "/api": {
    "target": "http://localhost:8080",
    "secure": false,
    "changeOrigin": true
  }
}

This was one of the bugs fixed this summer — the proxy was misconfigured and had to be corrected to get the frontend and backend communicating.

Section 19

Troubleshooting Guide

Backend won't start

Symptom

IntelliJ shows a compilation error or the Spring Boot application crashes on startup.

Check first: Look at the error message in the IntelliJ console. Common causes:

  • Missing or wrong Java version — Spring Boot 4 requires Java 17 or later. Run java -version.
  • application.properties has a missing or wrong Azure credential — look for a "connection refused" or "authentication failed" message.
  • Maven dependency download failed — check your internet connection and try refreshing Maven in IntelliJ.

Frontend shows network errors / API calls fail

Check: Is the backend running on port 8080? Is proxy.conf.json configured to point to http://localhost:8080? Start the Angular server with the proxy flag: ng serve --proxy-config proxy.conf.json.

Conversations not saving to database

Check:

  1. In Chrome DevTools → Network, confirm the POST /api/chat request includes a non-null employeeId
  2. In IntelliJ console, check for "Saving chat log" log line — if missing, the save is not being triggered
  3. Check the database credentials in application.properties are correct
  4. Check SSMS — can you connect to the database manually?

Sidebar shows no conversation history

Check:

  1. Confirm that employeeId is not null (see above)
  2. In Chrome DevTools → Network, look for the GET /api/chatlogs/{employeeId} request — is it being made? What does it return?
  3. In SSMS, check: SELECT * FROM dbo.chatlog WHERE employee_id = 'your@email.com' — are there records?

Employee login fails / MSAL errors

Check: MSAL configuration (client ID, tenant ID, redirect URI) in the Angular app. These must match the Azure AD application registration. Contact Larisa or Manish — they have access to the Azure AD portal to verify the registration settings.

Azure content filter blocks a query

If valid child welfare queries are being blocked, the Azure OpenAI content filter configuration may need to be updated. This is done in the Azure OpenAI resource settings in the Azure portal. Contact the team — this requires Azure admin access.
